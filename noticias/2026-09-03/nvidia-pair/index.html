NVIDIA lanzó PAIR en beta el 3 de septiembre y publicó la versión 1.0 el 13 de octubre de 2026. El router gratuito suma llama.cpp, modelos GGUF y RTX Spark; reparte solicitudes independientes entre equipos, pero no fusiona memorias GPU.

Actualización de octubre: de la beta a PAIR 1.0

El 3 de septiembre de 2026 NVIDIA presentó PAIR como beta de código abierto. El 13 de octubre publicó PAIR 1.0.0, un cambio material de disponibilidad y capacidades confirmado tanto por el comunicado del fabricante como por la versión firmada en GitHub. Esta página conserva la fecha, el ID y el eventKey originales para no fragmentar la cronología del mismo producto. La nueva versión incorpora soporte para llama.cpp, opciones para configurar el arranque de motores, una experiencia de terminal revisada y compatibilidad validada con el chip RTX Spark N1X. Los instaladores ya están disponibles; no se trata de una promesa de acceso futuro.

El router ahora puede instalar y administrar tres motores conocidos: Ollama, LM Studio y llama.cpp. Con este último permite buscar y descargar modelos GGUF compatibles desde Hugging Face, elegir argumentos de ejecución y distribuir solicitudes a equipos emparejados. Los puntos de acceso locales contemplan formatos Ollama, OpenAI y Anthropic Messages según el motor. Esto facilita usar clientes y agentes diferentes sin tener que decidir manualmente en cada uno qué PC ejecutará el modelo. No significa que todos los motores admitan cualquier modelo o función; la compatibilidad se comprueba por motor, versión y equipo.

La versión 1.0 también reorganiza la interfaz de terminal para administrar nodos, motores y modelos, e incorpora una vista Jobs que permite comprobar qué máquina atendió cada petición. Esa observabilidad es esencial para un laboratorio de agentes: ver cinco subagentes en pantalla no demuestra que estén usando cinco aceleradores distintos. NVIDIA distribuye instaladores firmados para Windows, paquetes Debian para Linux y DMG para macOS, además del código abierto con licencia Apache 2.0. PAIR es gratuito, pero los costes de hardware, electricidad y mantenimiento continúan. La compañía no publicó un benchmark independiente que garantice aceleración universal.

Compatibilidad y advertencias al actualizar

La documentación actual cubre Windows 11, Linux y macOS, con arquitecturas x64 y ARM64. Windows on ARM sigue señalado como experimental, aunque NVIDIA validó PAIR 1.0 con llama.cpp y CUDA sobre RTX Spark N1X. La página oficial enumera GeForce RTX serie 20 o posterior, DGX Spark, RTX Spark y equipos Mac M1 o posteriores como configuraciones validadas; especifica 4 GB de RAM mínimos y recomienda 500 MB de almacenamiento sin contar los modelos. La instalación del router no cambia los requisitos de memoria y controladores de cada motor o modelo. Un equipo con PAIR instalado puede no estar en condiciones de atender una petición concreta.

Las máquinas se conectan en una red local mediante emparejamiento y un código de seis dígitos. El fabricante describe inferencia privada, pero esa condición depende de que el cliente, los modelos y las herramientas del agente permanezcan realmente locales. PAIR no impide por sí mismo que una integración use APIs externas o comparta documentos con otro servicio. Para tareas sensibles conviene verificar destinos de red, permisos, acceso a puertos y registros de las solicitudes antes de habilitar automatizaciones. Tampoco convierte dos GPUs pequeñas en una sola GPU virtual: el repositorio aclara que cada petición independiente se dirige a un nodo.

La actualización introduce una incompatibilidad práctica: los endpoints locales pasan a respetar las políticas CORS de cada motor, en lugar de aceptar todos los orígenes de navegador. Una aplicación web puede requerir autorización explícita; NVIDIA cita OLLAMA_ORIGINS para Ollama. En macOS, la aplicación pasa a llamarse NVIDIA PAIR y puede instalarse junto a la antigua PAIR.app, por lo que debe seguirse la guía de migración. Los modelos descargados se conservan, aunque instalaciones antiguas de LM Studio pueden necesitar desinstalación manual separada. Revisar estos puntos antes de actualizar evita confundir una restricción de acceso con un fallo del router.

Análisis Gazette: cómo comprobar que sirve para agentes

Análisis Gazette: PAIR 1.0 reduce la fricción de reutilizar varios ordenadores para agentes que lanzan solicitudes independientes. La mejora es más clara en concurrencia y control operativo que en el tamaño de un único modelo. La compatibilidad con llama.cpp amplía opciones de formatos y cuantización; la vista Jobs ayuda a identificar saturaciones y nodos ociosos. Para una tarea que exige más memoria que la disponible en cada equipo por separado, PAIR no resuelve el problema mediante suma automática de VRAM.

La prueba correcta es ejecutar un conjunto fijo de diez o veinte peticiones con un nodo y después con dos o tres, manteniendo iguales el modelo, los prompts y los límites de tokens. Registrar tiempo total, latencia, errores, memoria y consumo permite distinguir el efecto del enrutamiento de la diferencia de hardware. También conviene desconectar un nodo durante una prueba reversible y observar la recuperación. Quedan pendientes benchmarks independientes, estabilidad bajo cargas persistentes y evolución de la compatibilidad con motores y plataformas.

El anuncio de NVIDIA en IFA 2026

El 3 de septiembre de 2026, durante la feria IFA, NVIDIA presentó Personal AI Router, abreviado PAIR, como una herramienta para compartir capacidad de inferencia de inteligencia artificial entre varios equipos de una misma red local. El software se describe como gratuito y abierto y su primera distribución es una beta. Es uno de varios anuncios que NVIDIA reunió ese día junto a noticias sobre agentes locales, llama.cpp, vLLM y nuevos equipos RTX Spark. PAIR merece una noticia independiente porque resuelve una necesidad distinta: coordinar solicitudes de modelos que ya ejecutan diferentes ordenadores.

La idea parte de una observación doméstica: muchos hogares y pequeños laboratorios cuentan con más de un PC y algunos permanecen desocupados durante parte del día. Un agente que lanza subtareas de documentación, programación y análisis puede generar varias llamadas simultáneas a modelos. Si todas llegan al mismo servidor, compiten por memoria y capacidad de procesamiento. PAIR descubre otros sistemas compatibles y enruta cada solicitud de inferencia a un nodo con capacidad, intentando aprovechar recursos ya disponibles sin trasladar necesariamente el trabajo a una nube pública.

Cómo distribuye solicitudes y qué no debe confundirse

PAIR se sitúa entre la aplicación que solicita una inferencia y los servidores locales que pueden realizarla. NVIDIA menciona Ollama y LM Studio como software compatible. La herramienta puede detectar ordenadores en una red privada, conocer la disponibilidad de recursos y seleccionar un destino para nuevas peticiones. Cuando un equipo entra o sale, la selección puede adaptarse. En una demostración descrita por NVIDIA, Hermes divide un encargo amplio en cinco subagentes; el router envía sus solicitudes a distintos PCs para que no aguarden todos por el mismo procesador gráfico.

Este enfoque se parece al balanceo de cargas de servicios informáticos, no a fusionar físicamente varias tarjetas en una sola GPU enorme. Si un modelo requiere más memoria que la disponible en un único nodo, PAIR no demuestra por sí mismo que sus pesos puedan repartirse entre memorias de otros PCs para ejecutar una única petición gigante. El beneficio esperado es más concurrencia y menor cola para tareas separables. El rendimiento depende del tamaño de cada modelo, velocidad de red, CPU/GPU de los nodos, número de trabajos y políticas de enrutamiento, por lo que no existe una aceleración universal garantizada.

Compatibilidad anunciada en septiembre: contexto histórico de la beta

La información oficial identifica interfaces gráficas y de terminal para Windows, macOS y Linux. Entre las plataformas compatibles figuran GPU GeForce RTX serie 20 o posteriores, tarjetas profesionales NVIDIA RTX PRO basadas en Turing o generaciones siguientes, NVIDIA DGX Spark y máquinas Apple con silicio M4 o posterior. Que una beta sea multiplataforma no significa que cualquier equipo antiguo con conexión Wi-Fi resulte elegible. También deben confirmarse versiones de drivers, sistemas de inferencia instalados, visibilidad entre nodos y permisos de acceso al conectar máquinas reales.

La disponibilidad anunciada es beta, no una certificación de estabilidad para operaciones empresariales críticas. El usuario debe comprobar la documentación de instalación actual y los modelos que ofrece cada nodo, evitando suponer que un modelo ausente se descargará o se convertirá automáticamente al formato apropiado. Las diferencias entre Ollama y LM Studio y la variabilidad de hardware generan límites operativos. NVIDIA no publicó una tarifa por tarea para PAIR en ese comunicado porque presenta el software como gratuito, aunque electricidad, redes y mantenimiento de varios equipos sí representan costes reales.

Rendimiento: separar la cifra de 1,9× del router

En el mismo anuncio, NVIDIA destacó que determinadas optimizaciones de llama.cpp podían ofrecer hasta 1,9 veces el throughput en una GPU GeForce RTX 5090 bajo sus condiciones de evaluación. También citó mejoras de vLLM en otros aceleradores. Esas cifras describen motores y kernels de inferencia, no una medición del rendimiento que PAIR garantiza al repartir tareas entre ordenadores. Agrupar todos los avances de una conferencia bajo un solo titular puede crear una causalidad falsa. El Gazette separa la mejora del backend de la capacidad de distribuir solicitudes concurrentes.

Para estudiar PAIR en la práctica hay que definir una línea base: cuánto tarda el mismo conjunto de trabajos de agentes si usa un solo equipo y cuánto tarda cuando puede aprovechar dos o tres. Deben medirse tiempo total hasta terminar la tarea, latencia por petición, throughput, porcentaje de fallos y consumo energético. Es importante mantener iguales los modelos, prompts y límites de tokens, porque añadir otro nodo con un modelo diferente altera también la calidad, no solo la velocidad. Un aumento de concurrencia no garantiza que cada respuesta individual salga antes.

Un artículo técnico adicional de NVIDIA aporta una demostración más específica de PAIR: cinco subagentes de Hermes Desktop ejecutados mediante Ollama y un modelo Qwen 3.6 35B A3B tardaron aproximadamente 18 minutos en una RTX Spark individual y 8 minutos con 48 segundos en un conjunto de tres dispositivos compuesto por un portátil RTX Spark, DGX Spark y RTX 5090. El proveedor etiqueta el ensayo como no oficial y dependiente de configuración, no como benchmark universal de escalamiento. El equipo debe distinguir este experimento del aumento de 1,9 veces que la otra nota atribuye a optimizaciones de llama.cpp.

Privacidad, permisos y observabilidad de agentes locales

La ejecución local puede disminuir la necesidad de enviar información a servicios de nube, pero PAIR modifica las fronteras internas de confianza. Una solicitud que antes se procesaba solo en el PC principal podría ser enviada a otro ordenador de la red. Conviene comprobar qué datos se transfieren, cómo se autentican los nodos, qué conexiones están permitidas y si las máquinas comparten usuarios o directorios sensibles. Una red doméstica tampoco equivale automáticamente a un entorno confiable; dispositivos invitados y equipos desactualizados pueden ampliar la superficie de exposición.

En un taller de agentes, además, la experiencia debería explicar qué nodo atendió cada petición, cuáles están disponibles y qué ocurre al desconectarse uno. Si el usuario debe interpretar puertos, procesos o archivos de log para saber si su solicitud llegó al servidor correcto, el sistema funciona técnicamente pero no es sencillo de administrar. Análisis Gazette: los routers locales ganarán valor si convierten varios ordenadores heterogéneos en un recurso fácil de observar y controlar, no solo si aumentan el uso agregado de GPU.

La documentación técnica añade que PAIR utiliza descubrimiento de nodos por mDNS, aprobación explícita de emparejamiento y cifrado mutuo TLS con certificados generados para comunicaciones entre equipos. El enrutador considera presencia del modelo, estado del motor, trabajos activos y ocupación de la GPU. Además, su vista Jobs permite identificar qué nodo ejecutó cada petición: contar cinco subagentes no prueba que realmente trabajaran cinco GPU, por lo que la telemetría de distribución es la evidencia necesaria. Estas salvaguardas son mecanismos anunciados que aún merecen revisión independiente en configuraciones reales.

Casos de uso y seguimiento responsable

El caso ideal es un conjunto de subtareas independientes: extraer información de documentos separados, analizar diferentes incidencias, clasificar mensajes o revisar módulos de un proyecto de software. En estos escenarios, la aplicación puede lanzar varias solicitudes a modelos sin requerir que cada subagente conozca de antemano la máquina que lo ejecutará. Conviene comenzar con tareas reversibles y datos no sensibles para verificar que el enrutamiento funciona y que los resultados conservan la calidad esperada al pasar entre nodos de hardware y configuración diferentes.

El seguimiento posterior deberá buscar pruebas reproducibles de latencia y escalamiento, evolución de la beta, soporte de más sistemas y controles de seguridad verificables. Para una organización pequeña el ahorro potencial puede provenir de reutilizar máquinas existentes; para un usuario con solo un PC, PAIR no proporciona por arte de magia hardware adicional. El anuncio del 3 de septiembre introduce una herramienta concreta para el problema de concurrencia local, pero su utilidad final debe demostrarse con cargas reales y no con cifras de rendimiento asociadas a otros componentes.

Análisis editorial

Consejos prácticos

  • Consultar las notas de versión y migración antes de instalar 1.0.
  • Comprobar CORS y OLLAMA_ORIGINS cuando se utilicen clientes web.
  • Probar dos nodos con el mismo modelo y medir Jobs, latencia, errores y tiempo total.
  • Verificar que los agentes no envíen datos sensibles a servicios remotos.
  • No confundir reparto de peticiones con fusión de memorias GPU.

Limitaciones

  • No suma VRAM ni divide una única inferencia entre varios PCs.
  • Cada motor/modelo conserva requisitos de memoria, sistema y controladores.
  • Windows on ARM permanece experimental.
  • Cambios de CORS pueden afectar clientes web existentes.
  • La privacidad depende de mantener todas las conexiones locales.
  • Sin benchmark independiente que garantice aceleración universal.

Resumen final

PAIR pasó de beta (3 de septiembre) a versión 1.0 (13 de octubre) con llama.cpp, descargas GGUF y una consola más útil. Su función es distribuir peticiones de agentes entre PCs locales, no fusionar VRAM. La adopción exige comprobar compatibilidad, CORS, privacidad y rendimiento real.

Qué seguir

Estabilidad de PAIR 1.0, compatibilidad Windows ARM, políticas CORS, rendimiento independiente y soporte de más motores.
