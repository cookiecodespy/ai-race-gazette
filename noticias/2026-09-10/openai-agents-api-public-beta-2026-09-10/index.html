Una infraestructura para agentes, no otro chatbot

El 10 de septiembre de 2026, OpenAI presentó Agents API en beta pública para desarrolladores. El anuncio abre una manera de construir agentes que pueden trabajar con herramientas, ejecutar código y conservar una sesión de larga duración sin que cada empresa tenga que crear desde cero su propia capa de orquestación. El componente central es el harness utilizado en Codex, ofrecido como servicio administrado. La noticia debe registrarse como lanzamiento de API y no confundirse con productos de voz, nuevas versiones del modelo o funciones exclusivas de ChatGPT.

La diferencia práctica es la responsabilidad operativa. Un modelo responde a instrucciones; un agente de trabajo también necesita elegir herramientas, gestionar errores, delegar tareas y conservar el progreso entre etapas. Con esta API, OpenAI asume parte del ciclo del agente, mientras el desarrollador sigue definiendo objetivos, permisos, datos, interfaces y entorno de ejecución. Esa separación puede acortar el tiempo de construcción, pero no convierte cualquier instrucción en un proceso seguro o confiable.

Qué se envía en una sesión

La documentación de lanzamiento describe la creación de una sesión a partir de una tarea, un modelo, herramientas y un entorno. Su ejemplo incorpora una herramienta de tipo MCP, una configuración de subagentes y un sandbox alojado. Esto importa porque el punto de entrada no se limita a una cadena de texto: el desarrollador declara explícitamente qué recursos puede utilizar el agente y bajo qué condiciones ejecutará su trabajo.

Las herramientas pueden ser integraciones MCP, funciones propias o capacidades incorporadas. En un sistema empresarial, esa lista debería ser mínima y estar ligada a permisos concretos. La posibilidad técnica de invocar un sistema externo no sustituye las comprobaciones de identidad, autorización, auditoría ni confirmaciones para acciones irreversibles.

El entorno puede ser de OpenAI o del cliente

La oferta distingue el harness gestionado del lugar donde corre el código. OpenAI presenta sandboxes propios y admite alternativas del desarrollador o proveedores asociados como Cloudflare, Daytona, E2B, Modal, Runloop, Vercel y otros. Algunas integraciones apuntan a entornos administrados y otras permiten desplegar dentro de una VPC. La elección afecta latencia, acceso a archivos, gestión de secretos, configuración de CPU o GPU y obligaciones de protección de información.

Este detalle evita una lectura equivocada: contratar el harness no obliga por definición a mover todos los sistemas internos a un único sandbox. Aun así, cada arquitectura requiere revisar por separado dónde se guardan archivos, qué credenciales recibe el agente y cuánto tiempo persisten sus resultados. No hay que tratar un entorno aislado como garantía automática frente a instrucciones maliciosas presentes en páginas o documentos.

Continuidad entre ventanas de contexto

OpenAI afirma que la API incorpora compactación automática del contexto cuando una sesión se acerca al límite del modelo. La idea es conservar la información necesaria para seguir trabajando durante varias ventanas. Para tareas extensas, esto reduce el trabajo de implementar resúmenes manuales cada vez que el agente acumula mensajes y resultados de herramientas.

Sin embargo, compactar no equivale a recordar perfectamente. Los resúmenes pueden omitir detalles y una aplicación seria debe persistir por fuera del modelo los artefactos, decisiones, entradas importantes, estados de ejecución y resultados verificables. Si un informe quedó escrito en un archivo, conviene leer ese archivo para confirmar su contenido; no basta con que el agente recuerde haberlo generado.

Herramientas y subagentes

La búsqueda de herramientas permite cargar definiciones pertinentes bajo demanda en lugar de insertar desde el comienzo catálogos enormes de funciones. Las llamadas programáticas pueden encadenar, filtrar o ejecutar operaciones en paralelo. El objetivo, según OpenAI, es evitar gasto innecesario de tokens y mantener el flujo de trabajo más eficiente, aunque el rendimiento real dependerá de la implementación y de las herramientas utilizadas.

En trabajos divisibles, un agente coordinador puede delegar investigación, inspección de código o análisis independiente a subagentes con contextos separados. La respuesta final debe reunir los resultados y resolver las contradicciones. Paralelizar puede reducir latencia en ciertos casos, pero también multiplica las superficies de acceso, el costo potencial y la necesidad de controlar quién hizo qué.

Apertura del harness y dependencia de proveedores

OpenAI describe el harness subyacente como código abierto y ofrece acceso a una base pública para inspeccionarlo. La versión gestionada sigue siendo un servicio de OpenAI, con infraestructura, mantenimiento y comportamiento versionado a cargo del proveedor. Son dos características distintas: poder leer la lógica básica facilita el aprendizaje y la inspección, pero no elimina la dependencia del servicio alojado.

Para decidir una arquitectura conviene separar componentes reemplazables: modelo, harness, herramientas, almacenamiento de estado y sandbox. Diseñar límites claros para estas capas facilita probar alternativas y evita que un cambio de modelo obligue a reescribir todo el sistema. La documentación del anuncio no demuestra por sí sola compatibilidad total con cualquier plataforma ni migración automática de sesiones.

Disponibilidad, precios y costes ocultos

La Agents API se anunció en beta pública para desarrolladores el 10 de septiembre, no como disponibilidad general definitiva. OpenAI señala que la API de agentes no tiene un recargo adicional propio; se factura el uso de tokens y herramientas según sus respectivas tarifas. En el foro oficial de desarrolladores, un representante aclara además que los contenedores alojados se cobran de acuerdo con las tarifas estándar de contenedores, separadas del consumo de modelos.

Por eso, no existe un precio total universal por agente o por tarea. Una gestión compleja puede incluir muchos pasos, subagentes, búsquedas, ejecución de código, almacenamiento y tiempo de infraestructura. Antes de construir un producto comercial hay que estimar coste por trabajo completado, límites presupuestarios, máximos de concurrencia y qué ocurre cuando una sesión queda abierta más de lo previsto.

Qué revelan los primeros testimonios

En el anuncio, distintos clientes reportan mejoras: Ciridae habla de menor latencia en su flujo, SafetyKit comunica una reducción de costo por caso y otras empresas destacan la gestión de sesiones largas o cargas variables. Se trata de testimonios seleccionados y publicados por OpenAI, no de una comparación independiente con metodología común. Cada cifra corresponde a un caso particular y no debería trasladarse automáticamente a otras organizaciones.

La señal interesante es que los usuarios citados describen problemas operativos —contexto, fallos, latencia, escala— y no solamente calidad de redacción. Para contrastar esas promesas, una empresa debe montar su propia evaluación repetible con escenarios de error, cancelación, recuperación, cambios de credenciales y verificación de resultados finales.

Implicaciones para desarrolladores y empresas

Para un equipo pequeño, la ventaja potencial está en prototipar un agente con menos servicios propios que mantener. Para una empresa regulada, los requisitos son diferentes: registro de operaciones, aislamiento de datos, gestión de secretos, límites de permisos, revisión humana y continuidad ante fallos. El mismo harness puede formar parte de ambos productos, pero la preparación para producción no se hereda de la API.

En el mercado de agentes, este anuncio desplaza parte de la competencia desde el modelo hacia la infraestructura que lo mantiene trabajando. El factor decisivo no será solo cuántas tareas inicia un agente, sino cuántas termina correctamente, con coste razonable y evidencia verificable. Pruebas recomendadas antes de adoptar

Una evaluación inicial útil puede incluir cinco pruebas: tarea corta con una sola herramienta; trabajo de varias horas con checkpoints; subagentes con resultados contradictorios; pérdida temporal de acceso al sandbox; y una acción externa que debe confirmarse antes de ejecutarse. En cada una, registrar tiempo, costo, estado final en el sistema de destino y posibilidad de reanudar sin duplicar efectos.

También conviene definir qué datos persisten fuera del contexto del modelo: identificador de ejecución, permisos efectivos, resultados de herramientas, archivos, revisiones y un criterio automático para declarar éxito. Una llamada de API exitosa no garantiza que la acción solicitada esté correcta en el repositorio, CRM o servicio externo. La aceptación debería basarse en una lectura verificable del estado de destino.

Qué sigue sin estar resuelto

El material oficial no permite asegurar que cualquier agente funcionará durante días sin errores, ni que un servicio alojado satisfaga por defecto todas las reglas de cumplimiento. La beta puede evolucionar antes de la disponibilidad general. Las organizaciones deben revisar cambios del SDK, política de datos, precios actualizados y restricciones aplicables a su cuenta antes de asumir una configuración estable.

Faltan comparaciones externas de fiabilidad, costes integrales bajo carga y recuperación ante errores de larga duración. Esas mediciones serán claves para saber cuánto de la complejidad desaparece realmente y cuánto simplemente pasa a administrarse por otro proveedor.

Análisis editorial

Consejos prácticos

  • Separar harness, modelo, herramientas, sandbox y almacenamiento de estado.
  • Probar fallos, cancelaciones y recuperación antes de permitir acciones sensibles.
  • Medir costo por tarea completada, no solo tokens por respuesta.
  • Verificar cambios externos mediante lectura independiente del estado final.

Limitaciones

  • Testimonios de clientes no constituyen benchmarks independientes.
  • Compaction no sustituye un registro externo duradero.
  • Beta sujeta a evolución y cambios operativos.
  • La API no aporta por sí sola aprobación humana ni verificación final en el sistema de destino.

Resumen final

El 10 de septiembre, OpenAI convirtió una capa operativa crucial de Codex en una API para desarrolladores. Abre una opción más rápida para desplegar agentes con herramientas y sesiones duraderas, pero la calidad de producto dependerá de permisos, observabilidad, costos totales y verificación real de resultados.

Qué seguir

Evidencia independiente de fiabilidad, costos por tarea, comportamiento de context compaction, estabilidad de la beta y compatibilidad al sustituir modelos o sandboxes.
