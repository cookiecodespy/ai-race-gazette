Decisions API lleva las respuestas tipadas al centro de las aplicaciones

La beta pública usa gpt-6-luna para clasificar, elegir entre opciones y evaluar contenido con respuestas estructuradas.

Abrir versión interactiva

Resumen ejecutivo

La Decisions API de OpenAI se presenta en beta pública como un endpoint especializado para transformar texto e imágenes en respuestas tipadas: probabilidades, elecciones entre categorías y puntuaciones sobre escalas. La documentación identifica a gpt-6-luna como modelo disponible y comunica una ventaja aproximada de velocidad frente a Responses API; esa comparación es una afirmación de OpenAI, no una prueba del Gazette.

OpenAI documenta Decisions como una API en beta pública que evalúa texto, imágenes o ambos y devuelve respuestas tipadas. En la versión consultada, gpt-6-luna es el modelo disponible y las solicitudes se envían a un endpoint dedicado.

La API ofrece tres tipos de pregunta: una condición con su probabilidad, una elección entre alternativas y una puntuación sobre niveles definidos. Esto permite usar el resultado en tareas como clasificación de contenido, enrutamiento de solicitudes o priorización.

Según OpenAI, estas respuestas son aproximadamente diez veces más rápidas que las de Responses API. Es una afirmación del proveedor; esta edición no la ha medido. Decisions está orientada a esas evaluaciones acotadas, mientras que otras herramientas de la plataforma cubren explicaciones libres y estructuras personalizadas.

En 30 segundos

  • La interfaz dedicada usa POST /v1/decisions y preguntas de tipo predicate, choice o score.
  • El proveedor anuncia una latencia aproximadamente diez veces menor que la de Responses API, sin que esta edición haya reproducido la medición.
  • Un resultado estructurado facilita el enrutamiento, pero las probabilidades deben calibrarse y las decisiones sensibles requieren controles humanos.

Qué cambia frente a una respuesta conversacional

La novedad de Decisions no es únicamente que un modelo pueda clasificar texto. Una aplicación que necesita cientos o miles de decisiones pequeñas normalmente tiene que pedir al modelo una respuesta estructurada y luego interpretar ese resultado. OpenAI propone una interfaz enfocada en preguntas acotadas para evitar tratar cada clasificación como una conversación completa. La documentación consultada describe una beta pública y el endpoint POST /v1/decisions, con gpt-6-luna como único modelo admitido en ese momento. Esta disponibilidad se distingue de la vista previa limitada anunciada originalmente el 29 de septiembre.

Cada solicitud reúne el modelo, una evidencia compartida en el campo input y una lista de preguntas. La evidencia puede ser texto o mensajes con texto e imágenes. Cada pregunta posee nombre identificable y tipo determinado; las respuestas llegan agrupadas en answers y conservan el nombre de referencia. Para un programador, ese contrato ayuda a conectar clasificación de documentos, moderación contextual, enrutamiento de tickets o análisis de fotografías a una lógica de aplicación. No convierte, sin embargo, una salida probabilística en verdad verificable.

Tres operaciones: condición, elección y escala

El tipo predicate estima mediante un valor entre cero y uno la probabilidad de que se cumpla una condición descrita. Google no participa en este anuncio: la especificación es de OpenAI, y sus propios ejemplos incluyen daños visibles sobre un producto. Choice selecciona una opción dentro de un conjunto cerrado, como el departamento correcto para una solicitud de asistencia. Score asigna una evaluación sobre niveles ordenados, por ejemplo una escala de gravedad; su resultado se calcula a partir de probabilidades sobre esos niveles y puede quedar entre dos valores. La distinción es relevante porque una categoría nominal no debe confundirse con una magnitud continua.

OpenAI orienta el endpoint a respuestas evaluativas, no a generar explicaciones largas o cualquier esquema arbitrario. La propia documentación dirige a Structured Outputs de Responses API cuando se necesita generar objetos según un esquema personalizado y a function calling cuando el objetivo es solicitar que el modelo use herramientas con argumentos. Por tanto, Decisions no reemplaza el resto de la plataforma. Elegirlo solo tiene sentido cuando los tipos predefinidos corresponden al problema que la aplicación necesita resolver.

Velocidad anunciada y coste de integración

OpenAI afirma que Decisions responde unas diez veces más rápido que Responses API para el trabajo que plantea. La cifra es un claim comercial y técnico del proveedor: esta redacción no examinó el benchmark, el hardware, la mezcla de entradas ni el tamaño de las solicitudes comparadas. Un equipo serio mediría latencias p50 y p95 sobre su conjunto de tareas, controlaría reintentos y fallos de red y compararía no solo rapidez sino calidad de las clasificaciones. El tiempo de cómputo menor deja de ser ventaja si aumentan los errores que obligan a revisión manual.

El precio final de usar una API depende de su tarifa vigente, volumen y patrón de datos; la guía de la función que se revisó no basta para atribuir un precio universal a cada decisión. Tampoco debe deducirse que la futura salida de beta esté garantizada en una fecha concreta: la página expresa una expectativa de lanzamiento general en semanas. Los equipos deberían programar una integración que pueda cambiar de versión y ejecutar pruebas de regresión antes de modificar reglas de producción.

Cómo usar probabilidades de forma responsable

Una probabilidad devuelta por un modelo puede ayudar a priorizar trabajo, pero su interpretación depende de calibración. Si una aplicación envía casos fáciles y difíciles en proporciones distintas, el umbral que funciona en la demostración puede fallar en producción. Conviene reunir un conjunto representativo etiquetado por personas, medir precisión y recuperación por segmento y revisar falsos positivos y negativos. En entornos de alto impacto se necesitan además reglas explícitas para que la decisión pueda derivarse a revisión humana.

El ejemplo más útil para una empresa quizá sea clasificar solicitudes en vez de delegar automáticamente resoluciones. Se puede usar choice para sugerir el equipo receptor y predicate para advertir de un riesgo, manteniendo registros del texto usado, de la respuesta y de las correcciones del operador. La trazabilidad permitirá saber si la API reduce el trabajo real y no solo el número de líneas de código. También conviene minimizar los datos enviados y separar el resultado estadístico del juicio de negocio que finalmente aplica una persona.

La lectura del Gazette

En una aplicación, muchas decisiones son pequeñas y repetidas. Una interfaz especializada puede simplificar su integración, pero las probabilidades requieren calibración y las reglas deben probarse con ejemplos del dominio real.

Análisis editorial

Consejos prácticos

  • Empezar con un conjunto etiquetado y comparar quality, costes y latencias contra la implementación actual.
  • Definir qué umbrales requieren intervención humana y registrar errores por categorías.
  • Usar Responses API con Structured Outputs cuando la tarea necesite un JSON arbitrario o explicaciones desarrolladas.

Limitaciones

  • Velocidad 10x: afirmación de OpenAI no comprobada de forma independiente aquí.
  • La beta y el único modelo disponible pueden cambiar; revisar versión, precios y disponibilidad antes de desplegar.
  • Las probabilidades no sustituyen calibración, auditoría ni revisión humana en decisiones sensibles.

Resumen final

Decisions API especializa una tarea de alto volumen en productos de IA: transformar evidencia en preguntas evaluativas con salida previsible. Su ventaja dependerá de que la rapidez anunciada se sostenga en pruebas reales y de que cada organización implemente calibración y controles adecuados. Su lanzamiento no debe confundirse con una solución general para toda decisión empresarial.

Qué seguir

Salida de la beta, mediciones propias de latencia y calidad de clasificación.
